How the Data Quality Assistant Was Built

Every line of application code here was written by AI coding agents — but under a written process, a task tracker the agents share, tests against the real dependencies, and a deterministic gate that decides when work is done. This page is the process; AI_USAGE.md is the fully-referenced log behind it.

01

A written workflow, not ad-hoc prompting

Development follows my own documented process for building greenfield software with AI agents — checked into this repo as software_development_workflow.md, with the short operating version in HOW_I_BUILD.md. Its first rule: before any agent writes code, the problem must fit in my head. I hold the compressed map; the spec and the task tracker hold the territory. The agent executes; judgment and scope stay with me.

This project ran the workflow at its FULL tier: sharpen the problem → challenge the plan → spec → learning tests → tasks with definitions of done → build under the gate.

Evidence: software_development_workflow.md · HOW_I_BUILD.md · HANDOFF.md §2
02

Spec-driven, decomposed into tasks

First a detailed technical spec — SPEC.md, 15 numbered features with observable acceptance criteria, explicit non-goals, and one end-to-end scenario. The spec was then decomposed into small tasks, each carrying a Definition of Done and the checks that prove it. The spec was frozen only after the learning tests ran (section 04), so no feature was designed on an unverified assumption.

Evidence: SPEC.md · task DoDs via bd show <id>
03

Beads: external memory for the agents

Task tracking is beads (bd) — an issue tracker built for coding agents, replacing Jira/Asana. Every task was filed as a bead; the agent claims it, works it, and closes it with a per-criterion close reason. Because beads live in a database the agent reads at every session start, they act as durable external memory: a fresh session knows what is done, what is next, and why past decisions were made. That is what makes long-running, multi-session work — and teamwork — possible.

The delegation unit was: one bead → one branch → one PR. Agents ran no state-changing git command; I reviewed and merged all fourteen PRs myself.

Evidence: bd list --status closed (41) · bd memories · PR bodies via gh pr view
04

Learning tests: verify the libraries before trusting them

This product leans on third-party dependencies — Great Expectations, the Claude Agent SDK, Supabase PostgreSQL. An agent will happily write code against a capability a library does not actually have, and the failure surfaces hours later. So before the spec froze, four learning tests ran small scripts against the real installed dependencies. Every one falsified an assumption the spec was about to be built on:

TestWhat it foundWhat changed
LT-1bRunning 10 rules over 500,000 rows takes 14.84 s — timed at 1k / 10k / 100k / 500k rows. Too slow to watch a blank spinner.Results stream progressively: first verdict at ~2 s, list fills in.
LT-1aA rule that could not run looks identical to a rule that failed.“Errored” became a third result state, never folded into “failed”.
LT-2aGE accepts 10 of 25 invalid rules without error (e.g. min=100, max=1).Our own validation table runs before GE ever sees a rule.
LT-2bThe model proposes rules that are statistically true but business-naive.Human review of AI proposals became a first-class product feature.

05

UX explored with a long-running agent harness

For the interface, I used Anthropic’s long-running-agent harness approach to generate four independent, complete UX variants — each a full HTML mock in design/. A three-judge agent panel then scored all four across compliance, expert usability, and buildability. I overrode the panel’s recommendation and picked the Workbench variant (design/ux-variant-workbench.html), because its side-by-side plain-English / compiled-rule layout is the product’s thesis — and I grafted in the mitigations the judges prescribed for its weak spot.

Generating several complete alternatives and judging them beats iterating on one draft — and the human still makes the call.
Evidence: design/README.md (scores) · UX_HARNESS_FINDINGS.md · PR #6
06

Dynamic workflows: a team of agents, not one

Features were built with Claude Code’s dynamic workflows — one orchestrating session spawning multiple sub-agents with distinct roles: one builds the task, one verifies it against the acceptance criteria, one reviews quality. It works like a small software team — developer, QA, reviewer, with the orchestrator as the manager — except the standup takes seconds and the reviewer never gets tired.

Evidence: session transcripts (recorded via SageOx) · wave PRs #12–#14
07

The right model for the right task

Model choice was deliberate: Claude Fable 5 for the critical, judgment-heavy work — generating the four UX variants, driving the multi-agent dynamic workflows — and Claude Opus 5 for straightforward implementation where the task is “write this well-specified code”. Matching model capability to task difficulty keeps both quality and cost honest.

08

The gate: what made delegation safe

None of the above is safe unless something deterministic decides when work is actually done. make check runs lint → format → typecheck → 187 unit checks in under 3 seconds, offline. On top of it sits an anti-cheat layer: a check that walks every test file with Python’s ast and fails the build on any test that asserts nothing or skips silently — so an agent cannot go green by writing hollow tests. The gate was deliberately broken and shown to block thirteen documented times before it was trusted.

Evidence: Makefile · tests/test_code_quality_thresholds.py · VERIFICATION.md §4
09

SageOx: the team layer

Sessions were recorded with SageOx, which makes the AI the coordination layer of a team: it listens to team discussions, turns them into transcripts a coding agent can read, and lets an engineer ask their agent “what was decided?” instead of chasing Slack threads. In this solo take-home it served as the session ledger; in a real team it replaces the email/Slack hop between a decision and the code change. Happy to demo it live.
