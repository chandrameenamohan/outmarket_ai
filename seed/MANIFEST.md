# Demo dataset — defect manifest

Ground truth for the seeded demo database. Generated by
`python3 seed/seed_demo_data.py --manifest` from the same constants the
seeder uses, so this file cannot silently drift from what is planted.

This doubles as the ground truth that later proves the rule engine finds
what is actually there. If a rule run reports fewer than the counts below,
the engine has a gap — the manifest is not adjusted to match it.

## Scale

| Table | Rows |
|---|---|
| `customers` | 50,000 |
| `orders` | 500,000 |
| `payments` | 500,000 (exactly one per order) |
| **total** | **1,050,000** |

500K orders, not the 2.4M quoted in the SPEC narrative: the Supabase free
tier is 500 MB and 500K is ample to measure GE latency behaviour (LT-1b).

## Planted defects

13 defect classes, 3,950 defective rows in total.
Every defect occupies a disjoint set of primary keys, so each count is
independently exact — no row carries two defects.

| ID | Table | Rows | Defect | Verified by |
|---|---|---|---|---|
| **D1** | `orders` | 150 | negative order_total — a sale that took money back | `SELECT count(*) FROM orders WHERE order_total < 0` |
| **D2** | `orders` | 320 | shipped_at earlier than ordered_at — shipped before it was ordered | `SELECT count(*) FROM orders WHERE shipped_at IS NOT NULL AND shipped_at < ordered_at` |
| **D3** | `orders` | 240 | status values outside the vocabulary — typos and casing drift (shippd, SHIPPED, compelted, in transit) | `SELECT count(*) FROM orders WHERE NOT (status = ANY(%(valid_order_status)s))` |
| **D4** | `orders` | 90 | orphan customer_id — order points at a customer that does not exist | `SELECT count(*) FROM orders o LEFT JOIN customers c USING (customer_id) WHERE c.customer_id IS NULL` |
| **D5** | `orders` | 60 | ordered_at in the future — clock skew / bad import | `SELECT count(*) FROM orders WHERE ordered_at > now()` |
| **D6** | `orders` | 150 | duplicate order_reference — 75 references issued twice (150 rows) | `SELECT coalesce(sum(n), 0) FROM (SELECT count(*) AS n FROM orders GROUP BY order_reference HAVING count(*) > 1) d` |
| **D7** | `customers` | 1,200 | missing customer email — cannot be contacted | `SELECT count(*) FROM customers WHERE email IS NULL` |
| **D8** | `customers` | 430 | malformed email — no @, no domain dot, trailing @, embedded space | `SELECT count(*) FROM customers WHERE email IS NOT NULL AND email !~ '^[^@[:space:]]+@[^@[:space:]]+\.[^@[:space:]]{2,}$'` |
| **D9** | `customers` | 260 | duplicate customer email — 130 addresses held by two accounts (260 rows) | `SELECT coalesce(sum(n), 0) FROM (SELECT count(*) AS n FROM customers WHERE email IS NOT NULL GROUP BY email HAVING count(*) > 1) d` |
| **D10** | `payments` | 410 | payment amount does not match its order_total | `SELECT count(*) FROM payments p JOIN orders o USING (order_id) WHERE p.amount <> o.order_total` |
| **D11** | `payments` | 200 | orphan order_id — payment for an order that does not exist | `SELECT count(*) FROM payments p LEFT JOIN orders o USING (order_id) WHERE o.order_id IS NULL` |
| **D12** | `payments` | 180 | payment method outside the vocabulary ('cred_card', 'PAYPAL', 'chq', 'Card ' — note the trailing space on the last one) | `SELECT count(*) FROM payments WHERE NOT (method = ANY(%(valid_payment_method)s))` |
| **D13** | `payments` | 260 | captured payment with no paid_at — money taken, no timestamp | `SELECT count(*) FROM payments WHERE status = 'captured' AND paid_at IS NULL` |

## Can the v1 rule engine actually catch these?

HANDOFF §5: v1 is single-column and table-level rules only; multi-column
is deferred to v2. Against that scope:

| Reach | Count | Defects |
|---|---|---|
| v1 single-column catalog | 8 classes / 2,670 rows | D1, D3, D5, D6, D7, D8, D9, D12 |
| needs a row_condition (not plain single-column) | 1 class / 260 rows | D13 |
| needs multi-column / cross-table (v2) | 4 classes / 1,020 rows | D2, D4, D10, D11 |

**1,280 known-bad rows are invisible to a purely single-column rule
set.** A demo that runs only v1 rules will call these tables cleaner than
they are. That is an argument for surfacing the multi-column gap in the
product, not for quietly dropping the defects.

Mapping to the curated catalog (SPEC O-1, finalised by LT-2a):

| ID | Expectation that would catch it |
|---|---|
| D1 | `expect_column_values_to_be_between(order_total, min=0)` |
| D2 | `pairwise A<=B (no single-column form)` |
| D3 | `expect_column_values_to_be_in_set(status, VALID_ORDER_STATUS)` |
| D4 | `referential integrity (no single-column form)` |
| D5 | `expect_column_values_to_be_between(ordered_at, max=now)` |
| D6 | `expect_column_values_to_be_unique(order_reference)` |
| D7 | `expect_column_values_to_not_be_null(email)` |
| D8 | `expect_column_values_to_match_regex(email, RFC-ish)` |
| D9 | `expect_column_values_to_be_unique(email)` |
| D10 | `cross-table amount reconciliation (no single-column form)` |
| D11 | `referential integrity (no single-column form)` |
| D12 | `expect_column_values_to_be_in_set(method, VALID_PAYMENT_METHOD)` |
| D13 | `expect_column_values_to_not_be_null(paid_at) WHERE status='captured'` |

## Vocabularies

- Valid `orders.status`: `pending`, `paid`, `shipped`, `delivered`, `cancelled`, `returned`
- Planted invalid: `shippd`, `SHIPPED`, `compelted`, `in transit`
- Valid `payments.method`: `card`, `paypal`, `bank_transfer`, `apple_pay`, `gift_card`
- Planted invalid: `cred_card`, `PAYPAL`, `chq`, `Card `
- Valid `payments.status`: `captured`, `refunded`, `failed`, `pending`

## Schema

Note what is deliberately absent. `orders.customer_id` and
`payments.order_id` are not foreign keys; `orders.order_reference` and
`customers.email` are not unique. Each of those constraints would make a
planted defect impossible. Only primary keys are indexed — extra indexes
would inflate the footprint and distort the LT-1b latency measurement.

```sql
DROP TABLE IF EXISTS payments;
DROP TABLE IF EXISTS orders;
DROP TABLE IF EXISTS customers;

CREATE TABLE customers (
    customer_id   integer       PRIMARY KEY,
    full_name     text          NOT NULL,
    email         text,                       -- nullable + not unique: D7, D8, D9
    signup_date   date          NOT NULL,
    country       text          NOT NULL,
    loyalty_tier  text          NOT NULL
);

CREATE TABLE orders (
    order_id        integer       PRIMARY KEY,
    order_reference text          NOT NULL,   -- deliberately NOT unique: D6
    customer_id     integer       NOT NULL,   -- deliberately NOT a foreign key: D4
    ordered_at      timestamptz   NOT NULL,
    shipped_at      timestamptz,
    status          text          NOT NULL,
    order_total     numeric(10,2) NOT NULL,
    currency        text          NOT NULL,
    channel         text          NOT NULL,
    ship_country    text          NOT NULL
);

CREATE TABLE payments (
    payment_id  integer       PRIMARY KEY,
    order_id    integer       NOT NULL,       -- deliberately NOT a foreign key: D11
    method      text          NOT NULL,
    amount      numeric(10,2) NOT NULL,
    status      text          NOT NULL,
    paid_at     timestamptz
);
```

Measured 2026-08-16 against PostgreSQL 17.6 on Supabase `ap-southeast-1`
(Singapore) from a laptop. Round-trip network time is included in every
number above and is expected; it is not worth chasing.

## Idempotency

The seeder drops and rebuilds all three tables from a fixed RNG seed
(`SEED = 20260816`), so re-running produces the same bytes rather than
doubled rows. Proof is a per-table content fingerprint — md5 over every
row in primary-key order, session timezone pinned to UTC:

```
customers  256cf549478c02a7192474eac6e70b99
orders     7b2f20d842bd4a4908d8ec8a625ea791
payments   100abbc4b03e55792ea1d2019d9827b4
```

Two consecutive full runs on 2026-08-16 produced exactly these three
hashes and identical row counts. Reproduce with:

```bash
python3 seed/seed_demo_data.py              # seed + verify
python3 seed/seed_demo_data.py --fingerprint
```

Reported table sizes can wobble by a few kB between runs (6008 kB vs
6016 kB for `customers`) — that is page/free-space-map bookkeeping after
a drop-and-recreate, not a difference in the data. The fingerprints are
the authority.

## Time-sensitive defect

**D5** plants `ordered_at` between 30 and 400 days after the 2026-08-16
anchor, and is verified with `ordered_at > now()`. Its count decays if
the data is left in place for more than ~30 days. Re-seed before a demo.
